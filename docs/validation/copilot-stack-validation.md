## 1. Trust model soundness — FAIL

The intended agent settlement path has substantial server-side controls. `POST /api/agents/prepare-settlement` takes only an outcome ID and creates its amount from the persisted formed team's `total_usd` ([prepare-settlement.ts, lines 60–80](/home/runner/work/outcomepay/outcomepay/functions/api/agents/prepare-settlement.ts#L60-L80)). `POST /api/agents/settle` requires a database, a settlement record, fresh PASS verification (re-running deterministic checks if stale), a recorded approval, and an APPROVED/AUTHORIZED PayPal order before capture ([settle.ts, lines 51–120](/home/runner/work/outcomepay/outcomepay/functions/api/agents/settle.ts#L51-L120)). The policy engine is the caller that authorizes/captures this order; amount is not accepted in either settlement request body ([settle.ts, lines 31–39](/home/runner/work/outcomepay/outcomepay/functions/api/agents/settle.ts#L31-L39), [prepare-settlement.ts, lines 19–23](/home/runner/work/outcomepay/outcomepay/functions/api/agents/prepare-settlement.ts#L19-L23)). Settle checks the PayPal order status but does not compare the live PayPal order or authorization amount with the persisted settlement amount before capture ([settle.ts, lines 92–120](/home/runner/work/outcomepay/outcomepay/functions/api/agents/settle.ts#L92-L120); [paypal.ts, lines 208–223](/home/runner/work/outcomepay/outcomepay/functions/_core/paypal.ts#L208-L223)).

The human gate is not actually protected as a human gate. `/api/agents/approve` has no authentication check and accepts a caller-provided `approver` string, defaulting it to `"human"` ([approve.ts, lines 18–59](/home/runner/work/outcomepay/outcomepay/functions/api/agents/approve.ts#L18-L59)). The MCP path authenticates its own requests, but then invokes this same REST endpoint; ordinary REST writes are not authenticated. Thus any caller, including an LLM, can create the approval record that settlement treats as human authorization ([mcp.ts, lines 157–166 and 176–195](/home/runner/work/outcomepay/outcomepay/functions/mcp.ts#L157-L195); [llms.txt, lines 47–48 and 54–70](/home/runner/work/outcomepay/outcomepay/public/llms.txt#L47-L70)).

The legacy PayPal routes block orders found in the settlement table, but only when `getDb()` returns a database. Both authorize and capture continue to the PayPal API when there is no DB handle, without failing closed ([authorize.ts, lines 24–42](/home/runner/work/outcomepay/outcomepay/functions/api/paypal/authorize.ts#L24-L42); [capture.ts, lines 29–58](/home/runner/work/outcomepay/outcomepay/functions/api/paypal/capture.ts#L29-L58)). The capture route accepts a caller-supplied authorization ID and its low-level capture helper has no policy check ([capture.ts, lines 26–57](/home/runner/work/outcomepay/outcomepay/functions/api/paypal/capture.ts#L26-L57); [paypal.ts, lines 185–223](/home/runner/work/outcomepay/outcomepay/functions/_core/paypal.ts#L185-L223)). This is a bypass if the database is unavailable while a settlement authorization exists. Also, prepare creates the external PayPal order before inserting the settlement record, so a persistence failure can leave an order that the legacy gate cannot identify ([prepare-settlement.ts, lines 71–90](/home/runner/work/outcomepay/outcomepay/functions/api/agents/prepare-settlement.ts#L71-L90)).

There are separate, intentionally generic PayPal harness routes: `create-order` accepts a caller-supplied amount, and the standalone authorize/capture endpoints can operate on orders not recorded as settlements ([create-order.ts, lines 20–45](/home/runner/work/outcomepay/outcomepay/functions/api/paypal/create-order.ts#L20-L45)). These do not bypass a *recorded* settlement's gate when the DB is healthy, but mean “only the policy engine touches money” is too broad unless explicitly scoped to agent settlement orders.

## 2. Approval freshness and lifecycle — FAIL

The expected sequential safeguards are present: approval rejects when the latest PASS predates an artifact ([approve.ts, lines 36–49](/home/runner/work/outcomepay/outcomepay/functions/api/agents/approve.ts#L36-L49)); delivery rejects an outcome already marked SETTLED and deletes an existing approval after replacing artifacts ([deliver.ts, lines 45–49 and 82–98](/home/runner/work/outcomepay/outcomepay/functions/api/agents/deliver.ts#L45-L98)); settle rejects an existing capture ID ([settle.ts, lines 68–70](/home/runner/work/outcomepay/outcomepay/functions/api/agents/settle.ts#L68-L70)). The two legacy routes return `policy_gated` for a settlement found in the database ([authorize.ts, lines 24–34](/home/runner/work/outcomepay/outcomepay/functions/api/paypal/authorize.ts#L24-L34); [capture.ts, lines 38–51](/home/runner/work/outcomepay/outcomepay/functions/api/paypal/capture.ts#L38-L51)).

These protections are not race-safe. Freshness compares millisecond timestamps using `<`; an artifact written in the same millisecond as the passing verification is not considered newer ([approve.ts, lines 42–48](/home/runner/work/outcomepay/outcomepay/functions/api/agents/approve.ts#L42-L48); [settle.ts, lines 72–86](/home/runner/work/outcomepay/outcomepay/functions/api/agents/settle.ts#L72-L86)). More importantly, settle reads the approval before remote PayPal calls and checks only `capture_id` immediately before capture; it does not atomically reserve settlement or re-read the approval/artifact/verification gates there ([settle.ts, lines 88–120](/home/runner/work/outcomepay/outcomepay/functions/api/agents/settle.ts#L88-L120)). Concurrent delivery or settlement requests can therefore invalidate evidence/approval or both pass the initial “not captured” check while another request is in flight. The second PayPal capture may be rejected by PayPal, but that is not an application-level exactly-once guarantee.

`prepare-settlement` also checks PASS and approval but does not itself check artifact freshness; the later settle check is what normally prevents capture on stale artifacts ([prepare-settlement.ts, lines 44–58](/home/runner/work/outcomepay/outcomepay/functions/api/agents/prepare-settlement.ts#L44-L58)).

## 3. Auth correctness — FAIL

The login start generates random state and a PKCE verifier, constructs an S256 authorization URL, and sets Secure, HttpOnly, SameSite=Lax cookies with a ten-minute lifetime ([login.ts, lines 10–24](/home/runner/work/outcomepay/outcomepay/functions/auth/login.ts#L10-L24); [agentid.ts, lines 48–75](/home/runner/work/outcomepay/outcomepay/functions/_core/agentid.ts#L48-L75)). The callback requires matching state and a verifier, then exchanges the code using client-secret basic authentication and PKCE ([callback.ts, lines 84–103](/home/runner/work/outcomepay/outcomepay/functions/auth/callback.ts#L84-L103); [agentid.ts, lines 86–111](/home/runner/work/outcomepay/outcomepay/functions/_core/agentid.ts#L86-L111)).

ID-token validation is not fail-closed. The verifier checks `alg=ES256`, issuer, exact-string audience, and expiration only when `exp` is a number; missing or wrongly typed expiration is accepted. It selects the first JWKS key when `kid` does not match ([agentid.ts, lines 149–189](/home/runner/work/outcomepay/outcomepay/functions/_core/agentid.ts#L149-L189)). The callback calls this “best effort,” renders the signed-in page even when verification returns invalid, and continues based on userinfo instead ([callback.ts, lines 95–113 and 124–129](/home/runner/work/outcomepay/outcomepay/functions/auth/callback.ts#L95-L129)). This does not substantiate a claim that the callback requires a valid ID token.

MCP and `/agent/identity` validate the token in the HTTP `Authorization: Bearer` header by asking AgentID userinfo; invalid or missing tokens get 401. MCP performs that check per request ([mcp.ts, lines 139–166 and 197–203](/home/runner/work/outcomepay/outcomepay/functions/mcp.ts#L139-L203); [identity.ts, lines 30–40](/home/runner/work/outcomepay/outcomepay/functions/agent/identity.ts#L30-L40)). This is a distinct access-token validation mechanism, not proof of the callback's ID-token validation. Per the operator's evidence, an authenticated MCP tool call has not been exercised; its live behavior is **NOT VERIFIED**.

## 4. Audit and idempotency claims — FAIL

The ledger hash is SHA-256 over the prior hash, event kind, and canonicalized payload; verification recomputes those links from a zero genesis hash ([ledger.ts, lines 28–50 and 100–117](/home/runner/work/outcomepay/outcomepay/functions/_core/ledger.ts#L28-L50); [verify-ledger.py, lines 37–57](/home/runner/work/outcomepay/outcomepay/scripts/verify-ledger.py#L37-L57)). This provides tamper evidence for those hashed fields in the supplied chain. It does **not** prove who created the entries, that the database/export is complete or immutable, or that the chain head is an externally trusted checkpoint. Entry IDs, sequence numbers, and timestamps are not included in the hash material, and verification does not check sequence continuity ([ledger.ts, lines 18–25, 48–50, 105–116](/home/runner/work/outcomepay/outcomepay/functions/_core/ledger.ts#L18-L25)). Both checked-in exports ([11-entry demo](/home/runner/work/outcomepay/outcomepay/ledger/out_mutdap0v6wtd83.json), [31-entry export](/home/runner/work/outcomepay/outcomepay/ledger/out_mv72gjbmtsytm3.json)) passed `python3 /home/runner/work/outcomepay/outcomepay/scripts/verify-ledger.py`; that confirms their present chain consistency, not the provenance of live settlement events. Describing this as a hash chain/tamper-evident log rather than a blockchain is accurate; treating an intact result as proof of authenticity or completeness would not be.

Sequential idempotency replay works as described: keys are scoped by endpoint, expire after 24 hours, and stored responses are returned with `Idempotency-Replayed: true` ([db.ts, lines 575–634](/home/runner/work/outcomepay/outcomepay/functions/_core/db.ts#L575-L634); [http.ts, lines 20–31](/home/runner/work/outcomepay/outcomepay/functions/_core/http.ts#L20-L31)). However, settle only looks up the key before doing work and stores its response after capture and ledger writes ([settle.ts, lines 55–60 and 116–174](/home/runner/work/outcomepay/outcomepay/functions/api/agents/settle.ts#L55-L60)). There is no in-flight key reservation or atomic settlement claim. Concurrent requests with the same or different keys can both reach capture before either persists a response/capture ID; therefore “write retries are safe” is true for completed sequential replays, not a general concurrency guarantee ([llms.txt, lines 91–97](/home/runner/work/outcomepay/outcomepay/public/llms.txt#L91-L97)).

## 6. Honest labeling — FAIL

The user-facing copy inspected consistently labels the prototype as not a legal escrow service and provider allocations as simulated, not PayPal Payouts (for example, [README.md, lines 16–20](/home/runner/work/outcomepay/outcomepay/README.md#L16-L20); [llms.txt, lines 38–41](/home/runner/work/outcomepay/outcomepay/public/llms.txt#L38-L41); [app/page.tsx, lines 79 and 137](/home/runner/work/outcomepay/outcomepay/app/page.tsx#L79-L137); [app/about/page.tsx, lines 49–56](/home/runner/work/outcomepay/outcomepay/app/about/page.tsx#L49-L56); [settlement-panel.tsx, lines 217](/home/runner/work/outcomepay/outcomepay/app/components/settlement-panel.tsx#L217); [prepare-settlement.ts, lines 65–69](/home/runner/work/outcomepay/outcomepay/functions/api/agents/prepare-settlement.ts#L65-L69)). No UI copy was found presenting OutcomePay as an escrow service; the “escrow” mentions are disclaimers or explicit statements that it is not one.

The sandbox-only assertion is not enforced by the code: `paypalConfig` deliberately switches to `https://api-m.paypal.com` when `PAYPAL_ENVIRONMENT=LIVE` ([paypal.ts, lines 23–24 and 63–70](/home/runner/work/outcomepay/outcomepay/functions/_core/paypal.ts#L23-L70)). Thus the labeling is honest about the default/deployed prototype only if operators guarantee the environment setting; source code permits real PayPal operation, contrary to the unconditional sandbox-only statements. The runtime mode of the live deployment was not independently verified.

## 7. Top risks — FAIL

1. **Approval is not authenticated or attributable to a human.** Any caller can POST an approval and choose the `approver` value. Add a server-verified approver identity/authorization check and bind approval to the verified evidence/version before allowing settle. Evidence: [approve.ts, lines 18–59](/home/runner/work/outcomepay/outcomepay/functions/api/agents/approve.ts#L18-L59).
2. **Capture policy is conditional on database visibility and not atomic.** Legacy routes fail open without a DB; prepare can leave an external order before its policy record exists; settle lacks a durable in-flight claim/CAS around capture. Fail closed if the policy record cannot be checked, persist or reconcile the order before exposing it, and atomically claim settlement before remote capture with a safe recovery path. Evidence: [capture.ts, lines 29–58](/home/runner/work/outcomepay/outcomepay/functions/api/paypal/capture.ts#L29-L58), [prepare-settlement.ts, lines 71–90](/home/runner/work/outcomepay/outcomepay/functions/api/agents/prepare-settlement.ts#L71-L90), [settle.ts, lines 112–124](/home/runner/work/outcomepay/outcomepay/functions/api/agents/settle.ts#L112-L124).
3. **Production PayPal is one environment setting away.** Either hard-reject LIVE for this prototype or explicitly revise all “sandbox only/no real money” claims and add a deliberate production-mode safety boundary. Evidence: [paypal.ts, lines 23–24 and 63–70](/home/runner/work/outcomepay/outcomepay/functions/_core/paypal.ts#L23-L70); [README.md, lines 62–69](/home/runner/work/outcomepay/outcomepay/README.md#L62-L69).
4. **OIDC callback treats ID-token verification as advisory.** Require a valid signature and mandatory, correctly typed time/audience/issuer claims before presenting successful authentication; validate key selection by `kid`. Evidence: [callback.ts, lines 95–113](/home/runner/work/outcomepay/outcomepay/functions/auth/callback.ts#L95-L113); [agentid.ts, lines 149–189](/home/runner/work/outcomepay/outcomepay/functions/_core/agentid.ts#L149-L189).
5. **Audit/idempotency evidence is weaker than “complete immutable audit” or exactly-once.** Anchor ledger heads outside the mutable store and validate sequence continuity; add in-flight idempotency/settlement reservation and recovery around PayPal calls. Evidence: [ledger.ts, lines 48–50 and 100–116](/home/runner/work/outcomepay/outcomepay/functions/_core/ledger.ts#L48-L50); [settle.ts, lines 55–60 and 116–174](/home/runner/work/outcomepay/outcomepay/functions/api/agents/settle.ts#L55-L60).
